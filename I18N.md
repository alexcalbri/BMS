# Multi-language (i18n) — specification

Single source of truth for the multi-language work. Branch `feature/i18n`. Read it fully before touching code.

## 1. Goals and rules

- Languages: Spanish `es` (source, default) and English `en`. Adding a third must only need new catalog files.
- Every user has a language; every company has a default language. Effective language of a request:
  user language → company default → `es`. Before login: the app's device language.
- **Spanish is the source and the key.** With language `es` every text is byte-identical to today, so the
  existing tests (≈2,100 assertions on Spanish text) keep passing unchanged. Do not rewrite Spanish texts
  "to improve them" — any change to a source string changes its key.
- A missing translation falls back to the Spanish source; it never fails and never shows a key.
- **Not translated**: customer data (names, addresses, emails, custom field values, imported content),
  anything typed by users except what §8 lists, log lines, exception messages for developers, MCP tool
  names/descriptions (stay Spanish for now), stored history/activity rows (stay as written),
  values the server parses (see §5).
- Never edit an applied migration (they are checksummed). New schema = new migration file.

## 2. Server API (package `com.ideasdeveloper.bms.server.i18n`, in Core)

```kotlin
object I18n {
    const val Source = "es"
    val Languages = listOf("es", "en")
    fun normalize(tag: String?): String?          // "en-US,en;q=0.9" -> "en"; unknown/blank -> null
    fun language(): String                         // language of the current request/job; default Source
    fun <T> withLanguage(language: String?, block: () -> T): T
    fun contextElement(language: String?): CoroutineContext.Element   // ThreadLocal.asContextElement
    fun register(namespace: String, language: String, entries: Map<String, String>)
    fun loadFrom(loader: ClassLoader, resourceDir: String, namespace: String) // reads <resourceDir>/<lang>.json for every non-source language
    fun translate(source: String, language: String = language()): String          // caller's namespace (below)
    fun translateIn(namespace: String, source: String, language: String = language()): String
    fun moduleNamespace(moduleId: String): String       // "<id>"
    fun extensionNamespace(extensionId: String): String // "extensions/<id>"
    fun callerNamespace(): String                       // namespace of the calling class
    fun namespaceOf(type: Class<*>): String
}

/** Translates a Spanish source text into the current language. Placeholders {0}, {1}… are replaced by args. */
fun tr(source: String, vararg args: Any?): String
/** tr with an explicit namespace (escape hatch for Core code that translates on behalf of a package). */
fun trIn(namespace: String, source: String, vararg args: Any?): String
/** Marks a literal for the catalog without translating it now (enum labels, vals). Returns it unchanged. */
fun msg(source: String): String
```

Rules for callers:

- `tr("Literal en español")` — **one string literal per call**, on one line, no `$` templates, no `+`
  concatenation inside the call. Variables go through placeholders: `tr("{0} de {1}", a, b)`.
  (A regex extracts the literals to check the catalogs.) `tr(variable)` is allowed when the variable
  holds a text that was marked with `msg("…")` or comes from a definition (§6).
- With language `es`, `tr` returns the source with placeholders replaced — exactly today's text.
- Texts evaluated once at class-load time (`val`, `object` fields, enum constructor args, `const val`)
  must not call `tr` there. Either turn them into functions/getters, or keep the Spanish literal wrapped
  in `msg("…")` (or plain for `const val`) and call `tr(x)` where it is shown.
- **Each package owns its translations.** Lookup is per namespace: `tr` resolves the namespace of the
  calling class and looks the text up in (1) that package's catalog, (2) Core's catalog, (3) as a last
  resort any other catalog (Core first, then registration order); no entry → the Spanish source. The
  namespace comes from the Kotlin package of the class that calls `tr`/`I18n.translate`:
  `com.ideasdeveloper.bms.modules.<id>…` → module `<id>`, `com.ideasdeveloper.bms.extensions.<id>…` →
  `extensions/<id>`, anything else → Core. It is found with a `StackWalker` (skipping `I18n`, `tr` and
  `Localization.kt`) and cached per class (`ClassValue`); lambdas, coroutines, inlined code and helpers
  count as the class that declares them, so a module's `fun label(x) = tr(x)` resolves to the module.
  With language `es` nothing is looked up. So the same Spanish word may have different English per
  package ("Alta": sign-up event in Core, "High" priority in compras/mantenimiento/tareas; "Activo":
  "Active" in most modules, "Asset" in mantenimiento; "Vencida": "Overdue" vs "Expired" in membresia).
  Inside ONE package a key still has one translation: if one package needs two meanings of a word,
  reword one source text.
- Core code that translates texts *of a package* uses that package's namespace explicitly:
  `I18n.translateIn(I18n.moduleNamespace(id), text)` / `trIn(...)` (definitions, manifests, theme and
  module names, stored permission titles). `localizedPayload`/`localized()` use the namespace of the code
  that calls them (or an explicit `namespace` argument); a host module that shows nodes built by an
  extension localizes them with `localizedFor(extension, nodes)` (the extension's namespace).
- Extension code runs inside a host module's request; its own `tr` calls resolve to the extension's
  namespace by class. A host helper it calls translates as the host.
- The request language is installed once by Core (Ktor interceptor reading `Accept-Language`, later
  overridden by the authenticated user's stored language when known). Modules never read headers.
- Background jobs, schedulers, mail and notifications have no request: wrap the rendering in
  `I18n.withLanguage(lang) { … }` using the recipient's language (§7).

## 3. Catalogs

Flat JSON object `{ "Texto fuente": "Translated text", … }`, UTF-8, keys sorted alphabetically, one file
per language and package:

| Package | File |
|---|---|
| Core | `server/src/main/resources/i18n/en.json` |
| Module `<id>` | `modules/<id>/server/src/main/resources/modules/<id>/i18n/en.json` |
| Extension `<id>` | `extensions/<id>/server/src/main/resources/extensions/<id>/i18n/en.json` |

The namespaced path is mandatory (class loaders are parent-first). Core loads its own at startup and each
module's/extension's through that package's class loader when it is loaded. Placeholders `{0}` must
appear in the translation too. Keep leading/trailing punctuation and capitalization style of the source.

Every package has a test (Core gives the utility `I18nCatalogCheck`) that extracts all `tr("…")` /
`msg("…")` literals from its sources plus its definition texts (§6) and fails when one is missing from
`en.json`, when placeholders differ, or when the catalog has entries nobody uses. Core's
`AllCatalogsTest` loads every catalog of the repository: it fails when a package uses a literal its own
catalog lacks (or uses `tr` without a catalog) and only *prints* keys that two namespaces translate
differently (allowed, see §2).

## 5. Values versus labels (server-driven UI)

The app posts back what it shows in several places, and servers compare it with Spanish text. Therefore:

- **Values stay in the source language**: `UiField.options`, `UiFieldCondition.values`, action `params`,
  filter values, tab/route ids, enum labels used as stored or parsed values, CSV/import headers.
- **Labels are translated**: `UiField.label/help/placeholder/section`, titles, subtitles, button labels,
  column headers, badges, empty texts, messages, errors, confirmation texts.
- New optional contract field `UiField.optionLabels: List<String>? = null` (same size/order as
  `options`). The app shows `optionLabels[i]` and submits `options[i]`. Same idea wherever another node
  carries options that are both shown and sent back (add an equivalent optional `…Labels` field; older
  clients ignore it).
- Core offers `UiScreen.localized()` (and the same for the other top-level payloads): when the language
  is not the source it fills `optionLabels` with `tr(option)` for every field that has none, and
  translates default empty texts. Each module's response helper calls it right before
  `UiJson.encodeToString(…)`. It must not translate anything else by guessing — labels are translated
  explicitly with `tr` where they are created.
- A select whose options are user data (stage names, customer names, board names) gets no translated
  labels unless §8 applies.
- Where the server parses text it showed earlier (e.g. a status label coming back as a value), parse
  against the **source** labels only.

## 6. Module and extension metadata

`ModuleDefinition` (displayName, description, views, permissions, fields, actions titles) and the
extension equivalents stay written in Spanish. Core translates them at response time with `tr(…)` using
the catalogs; the package lists those texts in its `en.json`. Nothing in the definition classes changes.

## 7. User and company language

- `application_users.language` (nullable, core migration that applies to central and tenant databases)
  and `companies.default_language` (control migration, default `'es'`).
- `LoginSuccessResponse` carries `language` (effective) and `companyLanguage`.
- `PUT /auth/profile` accepts `language` (`es`, `en` or null = follow the company). Company default is
  changed in the Company module settings by who can already edit company data.
- `Accept-Language` is sent by the app on every request; for authenticated requests the stored user
  language wins when set.
- Notifications are stored rendered: Core's notifier gets an overload that takes a builder and runs it
  under each recipient's language (`userLanguage(tenant, userId)` → company default → `es`). Emails to
  staff use the same. Emails to customers keep their existing template/translation logic.

## 8. Dynamic translation of user-written text (stage names, notes)

Requested by the owner: stage names and notes are shown translated; **customer data is not**.

- Core service `TextTranslation` (package `…server.i18n`): `translate(tenant, texts, target): List<String>`
  with a tenant cache table `text_translations(hash, language, source_text, translated_text, manual,
  updated_at)`, primary key `(hash, language)`; hash = SHA-256 of the trimmed source text.
- The actual provider is registered by a module through a hook (`registerTextTranslator`); the CRM
  registers its existing provider (`CrmTranslate`, key in CRM settings). No provider or no key → texts
  are shown in the original, without error. Provider errors are swallowed (logged once) and never break
  a screen. Lookups on a screen are batched; only cache misses call the provider; a screen never waits
  more than a short timeout (misses are filled in the background and appear on the next load).
- Source language detection is not attempted: a text is sent only when the viewer's language differs
  from the company default language, which is assumed to be the language texts are written in.
- Stage names (and other short configuration names: pipelines, boards, categories, plan names): shown
  translated everywhere as labels; values stay original (§5). A manual translation can be stored
  (`manual = true`) from the stage editor and is never overwritten by the provider.
- Notes (free-text notes/comments written by staff in CRM, tasks, etc.): shown in the original with the
  translation available under it via a `translation` text in the node (optional contract field), so the
  original is never hidden. Notes that belong to customer data fields are not sent.
- Never send to the provider: customer names, emails, phones, documents, addresses, custom field values.

## 9. App (Compose Multiplatform)

- `tr("Texto")` in common code with an embedded English map (`Strings_en.kt` or similar), global
  observable language state stored with `PersistentPreferences`; initial value = device language.
- Language selector in Settings/profile (follows company / Español / English); saved through
  `PUT /auth/profile` and locally. After login the server's `language` wins.
- `Accept-Language` header added where the app-version header is installed.
- Renderer shows `optionLabels` and the note `translation`; remove text-sniffing hacks such as
  `label.contains("codigo")` in `NativeModuleRenderer.kt` (use a field type/flag instead).
- The app cannot be compiled in the agents' container; it is validated by the GitHub Actions build.

## 10b. Core implementation (0.10.0) — decisions and exact API

Everything below lives in `server/src/main/kotlin/com/ideasdeveloper/bms/server/i18n/` unless noted.

**Language of a request.** `installI18n()` (called first in `Application.module`) wraps every call in
`I18n.contextElement(lang)`. `lang` = the stored language of the session's user when Core already knows
it (in-memory `SessionLanguages`, filled at sign-in, on `PUT /auth/profile` and when a session is
validated), else `Accept-Language`, else `es`. When `ModuleAccessService` validates the session
(`requireModuleAccess`, `requireModulePermission`, `userSession`) it calls
`I18n.overrideRequestLanguage(storedLanguage)`; the holder in the coroutine element is mutable, so the
change made inside `withContext(Dispatchers.IO)` is seen for the rest of the request. No extra query
per request: the stored language is read once per user every 10 minutes (and never fails: before the
migration it counts as "none"). For an authenticated user without own language the app's
`Accept-Language` (= the effective language it got at login) is used.

**`tr` details.** `tr(source, args…)` formats `{n}` by position; `null` is written `"null"` (like a
Kotlin template, so texts converted from `"$x"` stay byte-identical); without args braces are left as
they are. `I18n.translate(source)` translates without formatting. `I18n.has(source, lang)` tells whether
an entry exists in any catalog, `I18n.hasIn(namespace, source, lang)` in one. Lookup: caller's namespace,
then Core, then any other catalog (§2); `I18n.translateIn(namespace, source)` / `trIn` choose the namespace.

**Catalog loading.** Core: `i18n/en.json` at startup. Modules: `ModuleRegistry` loads
`modules/<id>/i18n/<lang>.json` through each module's class loader when it is built; extensions:
`ExtensionRegistry` loads `extensions/<id>/i18n/<lang>.json` (namespace `extensions/<id>`). A test that
builds a module without a registry calls `loadModuleCatalog(module)` / `loadExtensionCatalog(extension)`.

**Contract (core/src/commonMain, ModuleUi.kt).** `UiField.optionLabels: List<String>? = null` and
`UiTimelineEntry.translation: String? = null` (translation of `body`, shown under it; notes, comments
and activity are timeline entries in every module — the only node that needed it). Both are omitted
from the JSON when null. Server side (`Localization.kt`): `UiScreen.localized()`, `UiNode.localized()`,
`UiField.localized()`, `UiSuggestions.localized()` (identity) and the generic `localizedPayload(x)`
(dispatches on the runtime type, also inside lists; anything else is returned unchanged). They fill
`optionLabels` with the translation of each option in the namespace of the caller (or the `namespace`
argument; `localizedFor(owner, x)` uses the namespace of `owner`'s class) for fields that have none (only when a label differs) and
translate the default empty texts `Sin datos.` / `Sin elementos.` / `Sin actividad.`. With `es` they
return the same instance.

**Metadata.** `ModuleDefinition.localized()` (name, description, views, field label/help/section,
action titles, permission title/description; select options stay) is applied by `/modules`,
`/modules/{id}/metadata`; theme names, notification module names, customer-history module names, the
server module list, company module list, permission list of the users screen (stored in Spanish in
`application_permissions`), extension summaries (name, description, setting label/help, uninstall
option labels) are translated at response time with the namespace of the module/extension they belong
to (`ModuleDefinition.localized()` uses `moduleNamespace(id)`, extension summaries `extensionNamespace(id)`). `definitionTexts(definition)` lists those
texts for the catalog check; `I18nCatalogCheck.manifestTexts(manifest)` does it for extensions.

**Storage.** Migrations: core `V006__add_application_user_language.sql` (central + tenants),
control `V014__add_company_default_language.sql`, tenant `V010__create_text_translations.sql`; applied
by `install.sh` / `update.sh` and, for companies, by provisioning and at startup.
`LoginSuccessResponse` adds `language` (effective), `companyLanguage` and `userLanguage` (own, null =
follows the company). `PUT /auth/profile` accepts `language`: `"es"`, `"en"`, `null` (follow the
company) — **left out means unchanged** (older apps); anything else → 400 `INVALID_LANGUAGE`.
`GET /auth/profile` returns `language` (own). Company default: `GET/PUT /companies/me` carry
`defaultLanguage` (PUT: null/left out = unchanged), and modules call
`access.companyLanguage(code)` / `access.setCompanyLanguage(code, lang)` (cached 5 min).
Helpers: `userLanguage(connection, userId)`, `companyLanguage(central, code)`,
`access.recipientLanguage(tenant, userId)` (user → company → `es`).

**Notifications.** `ModuleNotifier.notify(tenant, userId, target) { NotificationText(title, text) }`
and `notifyEach(tenant, userIds, target) { … }` run the builder under each recipient's language. The
old `notify(tenant, userId, title, text, target)` is unchanged (stores the text as given).
`ExtensionNotifier` has the same builder overload.

**Install states** (module/extension package installs) are rendered when shown, in the viewer's
language; build progress steps are marked with `msg()`. Build/validation details from the compiler
and the package validators (`ModuleBuildException`, manifest problems) stay Spanish (developer texts).

**Dynamic translation (`TextTranslation`, §8).** `access.textTranslation`:
- `translate(companyCode, tenant, texts, target = I18n.language()): List<String>` and the one-text overload;
- `noteTranslations(companyCode, tenant, notes): List<String?>` → put it in `UiTimelineEntry.translation`;
- `setManual(tenant, source, language, translated)`, `removeManual(…)`, `manualTranslations(tenant, sources, language)`.
Provider hook: `access.registerTextTranslator(id, TextTranslator { tenant, texts, source, target -> … })`
returning the translations (same size/order), `null` when the company has no provider/key, or throwing
on a provider error (logged once per company, then the provider rests 5 minutes). One cache query per
call; misses go in batches of 50 to the first configured provider on a background thread; the call
waits at most 800 ms. The CRM should register it in `routes()` with `CrmTranslate.load(tenant)` +
`CrmTranslate.translator(settings, CrmJavaHttp)` and `translate("", text, false, source, target).second`
per text (keeping its cooldown); Core never calls a provider when target == company default.

### How a module adopts i18n (checklist)

1. Wrap every user-facing literal: `tr("Texto")`, `tr("Hola {0}, tienes {1} tareas", name, count)`.
   One literal per call, no `$`/`+` inside. Values that are parsed back (options, statuses, params)
   stay Spanish and untranslated.
2. `val`/`object`/enum texts: keep them as `msg("Texto")` and call `tr(x)` where they are shown.
3. Response helper: `respondText(UiJson.encodeToString(serializer, localizedPayload(result)), ContentType.Application.Json)`
   (import `com.ideasdeveloper.bms.server.i18n.localizedPayload`). Error JSON: `tr("…")` in the message.
4. Selects whose options are shown and sent back get `optionLabels` for free; set them yourself only
   when the label is not `tr(option)`. User data options get none (or `access.textTranslation` for §8 names).
5. Notifications: `notifier.notify(tenant, userId, target) { NotificationText(tr("…"), tr("…", x)) }`.
   Jobs/mail to staff: `I18n.withLanguage(access.recipientLanguage(tenant, userId)) { … }`.
6. Catalog `modules/<id>/server/src/main/resources/modules/<id>/i18n/en.json` (extensions:
   `extensions/<id>/server/src/main/resources/extensions/<id>/i18n/en.json`): flat, sorted keys,
   same `{n}`; include the texts of the `ModuleDefinition` / `extension.json`.
7. Test (in the package's `server/src/test/kotlin`):
   ```kotlin
   @Test fun catalogIsComplete() = I18nCatalogCheck.assertModule("crm", CrmServerModule.definition)
   // extension: I18nCatalogCheck.assertExtension("<id>", <the extension>.manifest)
   // tr(variable) texts nobody lists: assertModule("crm", definition, extraTexts = listOf(...))
   ```
   English output tests: `I18n.withLanguage("en") { … }` (the module's catalog is loaded by
   `ModuleRegistry`; without one call `loadModuleCatalog(module)` first).
8. Bump the package version (minor) and `minCoreVersion = 0.10.0`.

## 11. Working rules for agents

  something you need, report it instead of patching Core.

## 10c. Clarifications after the pilot (Clientes)

- Step-by-step guide for a module or extension: `I18N_MODULE_GUIDE.md`.
- `const val Label = "Texto"` used for display: turn into `val Label = msg("Texto")` and show with `tr(Label)`.
- The catalog check requires every text the package uses in its own `en.json`, even when Core's catalog
  already has it. Each package owns its translations (§2): translate the text for **your** package's
  context (a priority "Alta" is "High" even though Core's "Alta" is "New item"). For identical sentences
  reuse the wording other packages already use ("Cancelled", "You do not have permission to view…") so
  the product reads the same.
- Extensions: the manifest has no `minCoreVersion`; an extension that uses `tr` sets `minModuleVersion`
  to the first bilingual release of its host module (that one has `minCoreVersion` 0.10.0), so it is never
  offered or built on an older Core.
- Errors are translated where they are thrown; code that compares a message with a constant compares
  against `tr(Constant)`.
- Text written to the database (activity, history, job errors, author "Sistema") stays Spanish.
- User-written notes shown as list rows: `UiListItem.translation` (same meaning as
  `UiTimelineEntry.translation`).
- Extra glossary: ficha → profile; registro (log) → log; "Registro de X" → "X log".
